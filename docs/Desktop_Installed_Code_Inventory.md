# Installed-code inventory preparation

The Windows x64 user-installer task now writes `HydraInstalledInventory.json` beside `HydraSetup.exe`. It is a deterministic, **unsigned build-evidence artifact** describing every file selected by the pinned Inno `[Files]` mapping for Hydra's normal unversioned user install. This is preparation for a future owner-signed installed-code trust record; the current helper and update channel remain disabled.

The hook runs after the setup task clears its output directory and writes installer-specific `product.json` with `target: "user"`, and before Inno compiles the installer. It includes the final executable and visual manifest, application scripts, native libraries, built-in extensions, resources, direct installer tools and policies, and that staged product record. It excludes the source tree's `product.json`, signing-summary notes, and any file that the pinned mapping excludes. Versioned, proxy, Appx, and other installer layouts refuse until mapped and reviewed. `scripts/desktop.mjs installer` compares the saved inventory with the inputs again after Inno exits and refuses differences observed by the two scans. It does not hold file and directory leases across Inno compilation; a transient replacement between scans is not ruled out.

Schema version 1 records Hydra version, user x64 target, source and pinned upstream commits, and an ordinal-sorted list of destination path, byte length, and SHA-256. The parser requires canonical JSON, exact fields, bounded counts and sizes, unique case-insensitive Windows-safe paths, and valid digests. Generation refuses symbolic links/reparse entries, multiple hard links, unsupported filesystem objects, missing required installer tools, case collisions, and changes observed through a file handle while it is hashed. `npm.cmd run test:installed-inventory` exercises synthetic installer inputs and tampering. `verify-tree` compares an exact payload-only tree with the manifest; it does not yet account for Inno-generated uninstall files, shortcuts, or user-created data in a real installation.

This document and its commit fields are **not authentication**. A same-user process can modify an unsigned manifest and installed JavaScript. The release design must first sign final payload executables, hash the final signed bytes, sign the full inventory under a compiled/reviewed trust root, embed that signed inventory in the installer, then compile/sign the installer and publish signed metadata binding its final hash and the inventory. The inventory and its signature must be excluded from their own file list. The current 64 KiB update-feed payload and its three-file `expectedFiles` field are not a substitute for this separate complete artifact. Exact packaged-to-installed equivalence and controlled signed release acceptance still require a disposable Windows installer run.
