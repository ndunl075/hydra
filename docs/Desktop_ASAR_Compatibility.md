# Windows ASAR compatibility probe

This is an opt-in, disposable investigation of the startup/code-load boundary required by [the signed update design](Desktop_Update_Channel_ADR.md). It is **not** a packaging migration or release acceptance. The normal installer still uses the loose Code OSS application tree, and the native update helper remains disabled.

Run `node scripts/desktop-asar-compatibility-probe.mjs <absolute path to built Hydra runtime>` on Windows. The script copies the runtime under `.test-build/asar-compatibility/run-<id>/runtime`; it never rewrites the input. It removes the empty legacy `node_modules.asar`, packs `resources/app` into `resources/app.asar`, leaves native `.node`, `.dll`, `.exe`, and `.cmd` entries unpacked, embeds the archive header hash into the copied executable's `INTEGRITY/ELECTRONASAR` PE resource, enables Electron's embedded-ASAR-integrity and only-load-app-from-ASAR fuses, and removes the copied loose `resources/app` fallback. `report.json` records the exact source and blockers. A version mismatch makes the result diagnostic only. This command needs a complete runtime built from the same Hydra source; it is not part of the normal desktop build.

`--experimental-electron-fs` is a second, probe-only option. It changes the bare-`fs` loader hook in the copied `out/main.js`, `out/bootstrap-fork.js`, and `out/cli.js` from `node:original-fs` to `node:fs` before packing. It does not modify the source runtime or normal desktop build. The global change may alter ordinary workspace ASAR handling, so a production adaptation must be scoped and tested.

## Observed result

The first local run used an older Hydra 0.16.0 runtime while this source was 0.22.0, so it is compatibility evidence, not current-version acceptance. The copied `app.asar` and PE resource/fuses were internally consistent. A hidden launch reached Electron main and a renderer, but the shared process and renderer repeatedly failed to resolve `resources/app.asar/extensions`. Code OSS computes that built-in path under the application root. Its `bootstrap-esm.ts` maps bare `fs` imports to `node:original-fs`; the disk file provider and `pfs` use those imports, so the extension scanner does not traverse the archive.

As a diagnostic, copying the same built-in extensions to `resources/builtin-extensions` in that disposable runtime and passing `--builtin-extensions-dir=<absolute path>` removed the scanner failure. The extension host log showed `nico-dunlap.hydra-agent-manager` activating on `onStartupFinished`. That override is **not** a release solution: the Hydra extension's JavaScript, manifests, and assets then load outside the archive integrity check. The existing user-selectable built-in-directory argument also needs a trust policy before any built-in identity can authorize an update. Electron's ASAR fuses protect the application archive, not arbitrary extension code or unpacked native files.

The probe-only `node:fs` variant scanned built-in extensions without the loose-directory override and reached Hydra activation from `app.asar/extensions/hydra-agent-manager/dist/extension.cjs`. Its runtime was still the older 0.16.0 build. In a separate disposable copy, flipping one byte in that packed entrypoint without changing the archive header or executable produced an `ASAR Integrity Violation` hash-mismatch log in the extension host. The same launch then attempted extension activation and reported a JavaScript `ReferenceError` at the altered line. The main process remained alive. **This observation does not prove fail-closed refusal before altered extension code executes; it contradicts that acceptance gate for this configuration.** The archive was copied before tampering and the input runtime was untouched.

Reproduce that mutation only against a generated probe run with `node scripts/desktop-asar-tamper.mjs <absolute path to run-...>`. The script requires the run to be directly under Hydra's ignored probe scratch directory, requires the archived Hydra entrypoint and its integrity hash, saves an exclusive archive backup, changes one byte, and writes `tamper.json`. Launch the copied `runtime/Hydra.exe` with a new `--user-data-dir` and `--extensions-dir`; inspect that profile's `exthost.log` for the mismatch and whether altered code reached activation. Do not run it against an installed Hydra runtime.

## Required follow-on gate

Keep the built-in extensions inside the integrity-checked archive if using this path. In a disposable current-version build, test archive-aware read, stat, directory enumeration, and realpath behavior for the exact installed `app.asar` root while preserving normal workspace filesystem semantics. A production patch should scope ASAR-aware operations to the installed archive. Cover the shared-process scanner, renderer, extension host, Hydra activation/resources, editor, terminal, native modules, restart, CLI compatibility, and ordinary workspace file operations. Investigate why the extension host continued after detecting the altered entrypoint; require process-level refusal *before* any modified code executes, including packed built-ins. Tamper the archive header, entrypoint data, and missing archive in each code-loading process. If that boundary cannot be established, evaluate Windows-protected package deployment rather than assuming a separately signed same-user updater is isolated from compromised Electron code. Inventory and authenticate every unpacked executable/native file separately. Rebuild and re-sign the final executable after embedding the archive hash; changing its PE resources invalidates any earlier Authenticode signature.

Only a fresh version-matched runtime passing those checks can support a packaging migration. It still does not replace the release owner's signing service, publication origin, and signed end-to-end upgrade acceptance.
