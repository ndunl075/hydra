# Signed desktop update metadata

`verifyDesktopSignedUpdate(rawEnvelope, current, trust, floor, now)` is the pure metadata-verification part of the [Windows update-channel decision](Desktop_Update_Channel_ADR.md). It reads only caller-supplied bytes and values. It does not fetch a channel, read or write the sequence floor, download an installer, verify Authenticode, stage files, start a process, or enable automatic updates.

The native host must supply `trust` from an immutable installed release configuration, `current` from the installed Hydra product/version, `floor` from durable host-owned state, and `now` from the host clock. Feed bytes, webviews, extensions, and workspace settings cannot choose the trusted key or reset the floor. The release-owner key and distribution origin are still absent, so this module is not wired to a public channel.

The envelope is UTF-8 JSON with exact keys `schemaVersion`, `keyId`, `payload`, and `signature`. `payload` is base64 of UTF-8 JSON. Both JSON encodings must round-trip byte-for-byte through `JSON.stringify`; this rejects duplicate keys and alternate number/escape spellings, while allowing different property orders. The signature is base64 Ed25519 over the exact decoded payload bytes. The verifier bounds raw size and nesting before parsing the envelope, bounds decoded payload size before signature verification, and parses payload JSON only after the installed key verifies its signature.

The signed payload binds schema version, Windows x64 user target, monotonic sequence, issue/expiry time, exact installer byte length, the existing version-1 update manifest, and SHA-256 inventory for `Hydra.exe`, `resources/app/product.json`, and the bundled Hydra module's `package.json`. The existing manifest parser separately checks Hydra identity, channel, newer version, installer hash, and its structural provenance. Stable refuses prereleases and any artifact name other than `HydraSetup.exe`. An older sequence or different payload at the same sequence refuses; the exact same candidate can be rechecked during recovery while it remains newer than the installed version.

The focused test generates a disposable Ed25519 key pair and proves valid acceptance plus signature tampering, wrong key, duplicate keys, oversized input, wrong target/channel, expiry, prerelease, equal version, sequence rollback/equivocation, and invalid installed-file paths. These fixtures do not establish release-owner key custody, trusted Windows signatures, an installer run, or a live distribution endpoint.
