# Windows ASAR compatibility probe

This is an opt-in, disposable investigation of the startup/code-load boundary required by [the signed update design](Desktop_Update_Channel_ADR.md). It is **not** a packaging migration or release acceptance. The normal installer still uses the loose Code OSS application tree, and the native update helper remains disabled.

Run `node scripts/desktop-asar-compatibility-probe.mjs <absolute path to built Hydra runtime>` on Windows. The script copies the runtime under `.test-build/asar-compatibility/run-<id>/runtime`; it never rewrites the input. It removes the empty legacy `node_modules.asar`, packs `resources/app` into `resources/app.asar`, leaves native `.node`, `.dll`, `.exe`, and `.cmd` entries unpacked, embeds the archive header hash into the copied executable's `INTEGRITY/ELECTRONASAR` PE resource, enables Electron's embedded-ASAR-integrity and only-load-app-from-ASAR fuses, and removes the copied loose `resources/app` fallback. `report.json` records the exact source and blockers. A version mismatch makes the result diagnostic only. This command needs a complete runtime built from the same Hydra source; it is not part of the normal desktop build.

## Observed result

The first local run used an older Hydra 0.16.0 runtime while this source was 0.22.0, so it is compatibility evidence, not current-version acceptance. The copied `app.asar` and PE resource/fuses were internally consistent. A hidden launch reached Electron main and a renderer, but the shared process and renderer repeatedly failed to resolve `resources/app.asar/extensions`. Code OSS computes that built-in path under the application root. Its `bootstrap-esm.ts` maps bare `fs` imports to `node:original-fs`; the disk file provider and `pfs` use those imports, so the extension scanner does not traverse the archive.

As a diagnostic, copying the same built-in extensions to `resources/builtin-extensions` in that disposable runtime and passing `--builtin-extensions-dir=<absolute path>` removed the scanner failure. The extension host log showed `nico-dunlap.hydra-agent-manager` activating on `onStartupFinished`. That override is **not** a release solution: the Hydra extension's JavaScript, manifests, and assets then load outside the archive integrity check. The existing user-selectable built-in-directory argument also needs a trust policy before any built-in identity can authorize an update. Electron's ASAR fuses protect the application archive, not arbitrary extension code or unpacked native files.

## Required follow-on gate

Keep the built-in extensions inside the integrity-checked archive. In a disposable current-version build, test archive-aware read, stat, directory enumeration, and realpath behavior for the exact installed `app.asar` root while preserving normal workspace filesystem semantics. The first experiment can remove the global bare-`fs` to `original-fs` remap in the disposable build to locate further consumers; a production patch should scope ASAR-aware operations to the installed archive. Cover the shared-process scanner, renderer, extension host, Hydra activation/resources, editor, terminal, native modules, restart, CLI compatibility, and ordinary workspace file operations. Then tamper with an archived Hydra entrypoint, archive header, and missing archive to demonstrate refusal before loading that code. Inventory and authenticate every unpacked executable/native file separately. Rebuild and re-sign the final executable after embedding the archive hash; changing its PE resources invalidates any earlier Authenticode signature.

Only a fresh version-matched runtime passing those checks can support a packaging migration. It still does not replace the release owner's signing service, publication origin, and signed end-to-end upgrade acceptance.
