# First-channel installed update identity

Hydra's enabled update service now checks its installation before a metadata request or a download confirmation. The first channel accepts only a built Windows x64 user installation at `%LOCALAPPDATA%\\Programs\\Hydra\\Hydra.exe` with the default `%APPDATA%\\Hydra` profile and a matching HKCU Inno uninstall record for Hydra's x64 user AppId. It requires the registered install path, display name, and version to match the running release. The observed installation, executable, and profile paths must be real paths of the expected file types; a changed path or reparse resolution refuses. The service checks again after the user confirms a download.

Portable/archive, custom `--user-data-dir`, redirected app data, system install, missing or mismatched registry, and malformed paths are out of scope for the first channel and fail closed. This is a main-process admission check, not authority for the native helper. The helper must derive the same installation and user identity independently. The distributed update trust remains disabled.

New durable update operations record binding-policy version 1, the user installer AppId, and the observed installation, executable, and profile paths. The journal rechecks this binding before returning a saved candidate or replacing a state write. It does not include the running app version, so an operation can remain inspectable after a valid upgrade. Older journal versions are parsed without assigning them an identity; recovery returns `review` for an active unbound operation, and normal reads or writes refuse to resume or rewrite it. A review UI is still needed. This binding is not proof of a Windows user SID or authority to execute an installer. The native helper must independently establish the SID and installation authority before any launch.
