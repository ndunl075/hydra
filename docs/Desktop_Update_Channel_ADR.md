# Windows update channel decision

Status: accepted architecture, implementation pending. Reviewed against Hydra `ab415b6dab359acd48fc61ea60fd1df79307efe8` and the pinned Code - OSS `1.113.0` source at `cfbea10c5ffb233ea9177d34726e6056e89913dc`.

Hydra will have one Windows x64, per-user **stable** update channel. Its trust boundary lives in Electron main and a small native install helper. The built application will continue to omit Code - OSS `updateUrl`. Hydra may reuse upstream update UI and lifecycle interfaces, but it will not enable upstream Windows download, cache, startup recovery, or installer execution by adding a URL. The pinned upstream path makes its checksum optional, can reuse a cached installer, and does not require Hydra's Authenticode signer. It also compares the editor commit rather than Hydra's release version. Upstream's `/mergetasks=runcode,!desktopicon,!quicklaunchicon` would conflict with Hydra's opted-in desktop-shortcut behavior.

## Installed trust and release identity

The app embeds immutable Hydra product identity, `stable` channel, `win32-x64` user target, approved HTTPS origin, metadata public key identifier and key, and allowed Authenticode signer identities. Settings, extensions, webviews, and feed data cannot alter these values, choose local paths, or supply installer arguments. `product.hydraVersion` is the update comparator; Code - OSS's API version remains separate. Packaging must prove the app executable, installer, product record, and bundled Hydra module agree on the Hydra release version. The build stamps the executable's PE `ProductVersion` after upstream packaging, and [disposable Windows run 35488927001](https://github.com/ndunl075/hydra/actions/runs/35488927001) passed `desktop:verify`, smoke, installer lifecycle, and distinct-version upgrade on [PR #132](https://github.com/ndunl075/hydra/pull/132). The installed product record now carries a disabled trust configuration; it cannot become an active channel until an owner-controlled HTTPS origin, Ed25519 metadata key, and Authenticode signer identities are supplied and reviewed. See [Desktop_Installed_Update_Trust.md](Desktop_Installed_Update_Trust.md).

## Authenticated metadata and artifact

Wrap the existing version-1 `parseDesktopUpdateFeed` manifest in a separately versioned Ed25519-signed envelope. Sign the exact UTF-8 payload bytes carried as base64. The signed payload binds product, channel, platform, architecture, install target, release version, monotonic release sequence, issue and expiry times, installer byte length, SHA-256, source/build provenance, artifact name, and expected installed executable/product/bundled-module inventory with exact digests. Bound raw envelope size and nesting before parsing its strict outer JSON. Bound base64 and decoded payload sizes, then verify the signature against the installed key **before** parsing the signed payload JSON. Bound payload nesting, reject duplicate keys, and run the existing manifest parser as a second check. Its self-reported SHA-256 and `signature.status: "valid"` are structural claims, not publisher authentication.

The update service derives an immutable, hash-addressed artifact route from the installed HTTPS origin. Feed data supplies no arbitrary URL. Use normal TLS validation, no redirects for the first channel, bounded response size and time, and streaming hash/length checks. Persist the highest accepted release sequence and its content hash. Reject older sequences, different content at the same sequence, expired metadata, equal or older installed versions, prerelease versions on stable, and channel or target changes. An identical candidate at the same sequence may resume after interruption.

Metadata signing and Windows code signing use separate release-owner credentials. Build first; sign the executable, native helper, and installer; verify signatures; hash the final signed bytes; sign the metadata; publish immutable artifacts; and atomically advance the channel record. Feed-provided signer claims cannot extend the installed allowlist. Trust rotation requires a previously trusted Hydra release.

## Staging, consent, and recovery

Stage downloads in a dedicated per-user Hydra updater directory with restrictive ACLs, exclusive random operation directories, bounded disk use, and reparse-point refusal. The native helper takes a durable operation ID, not a renderer-supplied path or command. It verifies the actual downloaded bytes, Hydra product/version, and allowed signer using Windows Authenticode policy with an explicit timestamp and revocation policy; [`WinVerifyTrust`](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/nf-wintrust-winverifytrust) succeeds only on its explicit success return. Reverify cached bytes on recovery and immediately before execution, holding a verified handle that denies write/delete through process creation.

The first channel may check automatically but downloads on user request and installs only after **Restart to update**. Use native shutdown vetoes for unsaved work. A Hydra shutdown participant must save managed-session state and refuse an update if active provider work cannot stop safely. Serialize updater, helper, and installer operations for the target installation; block Hydra relaunch during the check-to-install window. The helper waits for all Hydra processes in that installation to exit, with bounded timeout and refusal. It starts the verified installer with constant, supported Inno arguments that prevent forced close, reboot, and installer-driven launch; the helper owns the later app restart. Add and test a Hydra-specific update mode in the pinned Inno script that preserves shortcut and task selections. Do not reuse upstream `/update=` semantics or its `!desktopicon` arguments. See [Inno Setup's command-line contract](https://jrsoftware.org/ishelp/topic_setupcmdline.htm).

Persist an atomic operation journal through `available`, `downloading`, `verified`, `awaitingRestart`, `installing`, `installed`, and `healthy`, with explicit refusal/failure states. No startup path runs a cached installer merely because a file or flag exists. Every helper launch binds to a user-authorized journal entry. Corrupt or uncertain recovery refuses and keeps evidence. Normal updates and new installers refuse downgrade/equal-version or mismatched installation identity; they must not overwrite a system/archive install. A same-version repair is a separate explicit authorization for the exact previously authenticated release bytes, with its own journal state and checks, never an automatic retry. Post-install checks compare executable, product, and bundled module digests against the signed installed-file inventory. Restart only after successful installer exit and verification. Failed or reboot-required outcomes retain evidence without launching or automatically replaying installation. A launch acknowledgment proves basic health only. A failed Inno overwrite is not an automatic rollback: preserve user data and diagnostics, then allow only that reviewed repair or a signed forward release. Historical installers cannot retroactively enforce the new downgrade guard.

## Delivery slices

Each row is a separate reviewed feature PR. Fixture trust roots can support the first three without activating a public channel.

| Slice | Deliverable | Acceptance |
| --- | --- | --- |
| 1 | Installed update configuration and consistent Hydra PE/product/installer/module release identity | Absent owner values fail closed; all version identities agree. |
| 2 | Signed envelope verifier around the existing parser | Tampering, duplicate keys, wrong key/target/channel, expiry, replay, downgrade, and stable prerelease refuse. |
| 3 | Bounded HTTPS fetch and private staging | Redirect, oversize/truncation, cancellation, disk/path/reparse failure, and changed cached bytes refuse. |
| 4 | Native signature verifier and install helper | Signed fixture passes; unsigned, wrong signer, revoked, tampered, unverifiable, and replacement-race fixtures refuse under the declared timestamp/revocation policy. The verifier's conservative leaf-time/EKU and WinTrust cleanup policy has fixture coverage; the packaged helper still refuses every invocation. Controlled revoked/timestamped release artifacts and authenticated main/helper handoff remain pending. |
| 5 | Inno update mode and downgrade guard | Disposable selected/unselected shortcut cycles retain choices; no forced close, reboot, launch, or downgrade. |
| 6 | Main-process update service, UI, shutdown veto, and durable recovery | Install requires verified user-authorized state; dirty work/active agent/corrupt journal refuse. |
| 7 | Controlled signing and atomic publication | Final signed-byte provenance and independent preflight pass; secrets stay out of logs. |
| 8 | Disposable signed release acceptance | Install N, update to N+1, restart, preserve data and shortcuts, refuse N/equal/tampered/wrong-channel or signer, and recover from interruption. |

The release owner must still supply the Authenticode publisher/signing service, timestamp and renewal policy, an owned HTTPS distribution origin, metadata-key custody/rotation, artifact retention, an initial signed stable version, a disposable Windows acceptance host, and release activation authorization. Until those inputs and the signed end-to-end test exist, Hydra has no automatic-update or signed-distribution acceptance claim.

The first [installed-code inventory increment](Desktop_Installed_Code_Inventory.md) emits a complete but unsigned manifest of the normal x64 user-installer payload after the installer-specific product record is staged. A later release must authenticate this separate inventory and verify the running main-process code before treating an IPC handoff as trusted; the existing signed feed's three-file inventory is insufficient. This increment does not change the disabled helper or the release gate above.

The next isolated increment adds a native, fixture-root ECDSA P-256/SHA-256 detached-signature check for the exact inventory bytes. The shipping entry point has no approved trust root and refuses, and the helper is still unlinked. Cryptographic byte authentication does not replace strict inventory parsing, installed-tree comparison, or proof of the code already loaded by Electron main. Those gates and the owner-controlled signed-release acceptance remain pending.

Native strict parsing of the retained authenticated bytes is now fixture-tested. Exact installed-tree lease verification and startup-established provenance remain separate gates; a process that loaded modified JavaScript and later restored its disk file must not become trusted merely because a later disk hash matches.

The native payload-tree fixture now verifies an exact snapshot under retained file handles. Windows blocked writes and renames of those files in the local test, but admitted a new file under the leased directory; re-enumeration detected it. Consequently this primitive cannot by itself establish lifetime-exact code loading. Before activating the helper, the release design must choose and prove a startup/code-load boundary, such as a reviewed [Electron application-ASAR integrity](https://www.electronjs.org/docs/latest/tutorial/asar-integrity) migration with [restricted load fuses](https://www.electronjs.org/docs/latest/tutorial/fuses), or a guardian with a separately enforced immutable code namespace. A post-hoc PID, IPC challenge, or disk hash is not sufficient.

The [disposable ASAR compatibility probe](Desktop_ASAR_Compatibility.md) confirms that packing the existing Code OSS tree is not yet a migration: its `original-fs` backed built-in extension scanner fails under `app.asar/extensions`. A loose built-in-directory override starts Hydra's extension host but removes archive integrity coverage for that extension. The archive-aware built-in path, unpacked-code trust, current-version runtime, and tamper/refusal acceptance remain open gates.
